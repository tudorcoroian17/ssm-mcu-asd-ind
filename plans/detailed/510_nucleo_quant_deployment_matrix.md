# Phase 5 Nucleo deployment matrix — six quantization schemes

**Feeds:** `06_phase_5_quantization_and_head.md` (handoff manifest: accuracy
and footprint at each rung, per board); `findings/150` (`ranges.json`, the
static-scale source); `findings/510` (streaming DMA -- why RAM headroom
changes what's cheap here); `findings/520`/`521` (weight-only Python
validation); `findings/522`/`523` (activation Python validation).

Everything in this document is Python-validated already. This is the plan
for turning that validation into six real, on-device artifacts with real
footprint and parity numbers -- the deliverable `06_phase_5...`'s handoff
manifest actually asks for.

## Decisions assumed -- correct these before starting if wrong

- **Item 3** (weight-only, per-channel) is assumed to mean `projections` mode,
  paired with per-channel granularity -- the direct granularity-only
  counterpart to item 1, holding weight-mode constant. `findings/521` also
  validated `all`/per-channel; if you want that combination deployed too,
  it is a seventh scheme, not a substitution for item 3.
- **Items 4-6**'s weight component is assumed to be item 1's scheme
  (`projections`, per-tensor) -- the cheapest, most conservative weight
  scheme, held constant while the activation axis varies. This isolates the
  activation effect on real hardware the same way `findings/522`/`523`
  isolated it in Python.
- **"Weight + activation using ranges" means a faithful port of the
  `--scale-source ranges` Python experiments**: int8 weight storage, static
  per-tensor activation scales, quantize-dequantize at each site, **compute
  stays fp32 throughout**. This gives flash savings from the weights and
  validated-accuracy behavior on real hardware; it gives no speed benefit,
  and is not a step toward one. True int8 arithmetic (real speed/power
  benefit) is explicitly **out of scope** for this plan -- it was never
  tested by any Python work here (which only measured quantization noise,
  not integer-arithmetic correctness), and would be a separate, much larger
  future effort if these results ever motivate it.

## How this maps to the escalation ladder

Every Python variant tested across `findings/520`-`523` stayed at rung 1
(post-training quantization) and left the primary metric within noise --
seven for seven. Nothing here escalates to rung 2 (mixed precision) or rung
3 (QAT); this phase is about producing the on-device numbers for the rung
already validated, not climbing further. If a real-hardware result
disagrees with the Python prediction for any scheme, that is the trigger to
reopen the ladder, not before.

## Folder layout

Your proposal -- `mcu/deploy/case<N>/<model>/` -- is the right shape. Two
refinements:

1. **Save `ssm_backbone.h`/`.c` in every model folder, not just the ones
   where it differs.** For items 1-3, the backbone C is identical across all
   three (see "Weight-only needs zero hot-loop changes" below) -- saving it
   three times costs nothing (flash/RAM are not remotely tight, per
   `findings/510`/`310`) and keeps every folder self-contained and
   uniform, so "which backbone.c goes with this weights.c" is never a
   question you have to reconstruct later.
2. **Add a `fp32/` folder per case** alongside the six schemes -- the
   unquantized baseline, generated by the same export script in its default
   mode. Every footprint and parity comparison needs a same-case fp32
   reference; keeping it in the same structure means you're never hunting
   for which historical run was the baseline.
3. **Drop a short `manifest.txt` in each model folder** recording the exact
   export-script invocation used to generate it (config, checkpoint, mode
   flags). Cheap now, and it is the difference between "I can regenerate
   this exactly" and "I think this is what I ran" six months from now.

Scheme folder names, for consistency:
```
mcu/deploy/case<N>/
fp32/
weight_int8_proj_pertensor/ (item 1)
weight_int8_all_pertensor/ (item 2)
weight_int8_proj_perchannel/ (item 3)
weight_act_boundaries_ranges/ (item 4)
weight_act_scan_ranges/ (item 5)
weight_act_all_ranges/ (item 6)
```


This is Nucleo-only. When Phase 3 starts on the ESP32 or RP2040, revisit
whether this needs a board-level folder above `case<N>` or a parallel
`mcu/deploy_esp32/` tree -- not a decision to make now.

## Weight-only needs zero hot-loop changes -- a design simplification worth using

`ssm_weights.h` declares every weight as `const float *`, and `ssm_block_step`
reads directly from those pointers on every frame. Nothing about weight-only
quantization requires touching that hot loop, because `findings/510` already
removed the RAM pressure that would have made this matter: **dequantize
every int8 weight array once at boot, into fp32 scratch buffers, and point
`ssm_block_step` at those buffers instead.** The per-frame math is then
byte-identical to today's code, for every one of items 1-3 -- per-channel
(item 3) only changes which scale value the boot-time dequant loop indexes
by, not anything about the frame loop.

Consequence: items 1-3 need exactly one new function
(`SSM_DequantizeWeights()` or similar, called once from `main()` before the
processing loop) and changes to `ssm_weights.h`/`.c`'s generated content.
`ssm_backbone.c` does not change at all across these three schemes.

## Activation quantization is not uniformly easy -- read this before estimating item 5's effort

Checked directly against `ssm_backbone.c`, not assumed:

| Python tensor | C form | Quantize effort |
| :--- | :--- | :--- |
| `u_post_conv_silu` | `u[SSM_D_INNER]`, materialized array | Loop once after computed -- easy |
| `z_gate` | `z[SSM_D_INNER]`, materialized array | Easy |
| `block_output` | `block_out[SSM_D_MODEL]`, materialized array | Easy |
| `final_norm_output` | `normed[SSM_D_MODEL]` in `ProcessFrame` | Easy |
| `delta` | `delta[SSM_D_INNER]`, materialized array | Easy |
| `B`, `C` | `B[SSM_D_STATE]`, `C[SSM_D_STATE]`, materialized | Easy |
| `A_bar`, `B_bar` | **Scalar temporaries inside the innermost `for c / for n` loop** (2048 iterations/layer/frame) -- never materialized as arrays | **Invasive**: insert a scalar quantize-dequantize call inside the hottest loop in the backbone |
| `h` | `state->h[layer][c][n]`, persistent but updated in that same inner loop | Same loop, same invasiveness |
| `y_scan` | **Does not exist as a separate quantity.** C fuses it directly into `y[c] = (y_c + u[c]*D[c]) * silu(z[c])` in one line | Must quantize the scalar `y_c` at the point it's computed, before the D-shortcut and gate are applied |

Every `boundaries` tensor is "easy." Every distinctly-`scan` tensor
(`A_bar`, `B_bar`, `h`, `y_scan`) is "invasive," because the Python model's
named intermediates don't exist as C values to hook -- they're fused into a
tight scalar loop for performance. **Item 4 (boundaries) and item 5 (scan)
are not equal-effort tasks despite looking parallel in the item list.** Do
4 first: it's the lower-risk way to validate the whole export → C → flash →
parity workflow once, before spending the larger effort on 5's loop surgery.
Item 6 (`all`) is very likely the union of 4's and 5's changes, not new work
of its own, once both exist.

**Claude comment:** the cycle budget almost certainly absorbs the extra
scalar quantize-dequantize operations in `scan`'s inner loop without issue --
`findings/510` measured 6.8x headroom, and a handful of extra float ops per
(channel, state) pair is small next to that margin. Worth measuring rather
than assuming, but I would not expect this to be the risk in item 5; the
risk is code correctness in a very tight loop, not timing.

## Task list, phased

### Phase 1 -- export script and generic weight dequant (unblocks items 1-3, `fp32`)

- Extend `export_ssm_weights.py` with `--dtype {fp32,int8}`,
  `--weight-mode {projections,all}`, `--granularity {per-tensor,per-channel}`
  (reusing `WEIGHT_MODE_SUFFIXES`/`quantize_dequantize`'s *quantization* logic
  from `checks/smoke/weight_quant_parity.py` -- but exporting the raw int8
  values and scale(s), not the dequantized float, since C needs to store the
  compact form). `--dtype fp32` with no other flags should reproduce today's
  output exactly -- a good regression check that the refactor changed nothing
  for the existing baseline.
- Extend `ssm_weights.h`'s generated struct: alongside (or instead of, per
  `--dtype`) each `const float *` weight pointer, emit `const int8_t *` +
  either a single `const float scale` (per-tensor) or a
  `const float *scale` array (per-channel, one entry per output row).
- Add the boot-time dequant function and the fp32 scratch buffers it
  populates. Point `ssm_block_step`'s existing `const ssm_block_weights_t *w`
  parameter at the dequantized struct, not the raw exported one -- no other
  line in `ssm_block_step` changes.
- Verify with `--dtype fp32` against the current, already-flashed firmware
  before touching int8 at all.

### Phase 2 -- items 1, 2, 3 (weight-only exports, per case)

For each of the four cases, each of items 1-3:
- Run the export script with the scheme's flags into
  `mcu/deploy/case<N>/<scheme>/`.
- Copy into the IDE project, build, flash.
- Parity: extend `check_backbone_parity.py`'s reference side (or add a small
  sibling script) to dump a *quantized* reference embedding for this exact
  scheme -- `weight_quant_parity.py`'s `build_embeddings(..., quantize=True,
  weight_mode=..., granularity=...)` already computes this; it just needs a
  `.npz` dump, mirroring what `dump_parity_vectors` does for the fp32 case.
  Compare device output against that scheme's own reference, not the fp32
  one -- weight-only's ~2% embedding drift (`findings/520`) is expected and
  correct; comparing against the fp32 reference would misread that
  expected drift as a bug.
- Footprint: repeat the `findings/440`/`510` Debug-build flash/RAM
  measurement per scheme.

### Phase 3 -- item 4 (boundaries, weight+activation)

- Extend the export script to also emit static activation scales for the
  `boundaries` group, sourced from `ranges.json` the same way
  `load_ranges_scales` does in `checks/smoke/quant/activation_quant_parity.py`.
  These are per-layer (block0's scales differ from block1's, per
  `ranges.json`), so add them to `ssm_block_weights_t` alongside the weight
  fields, plus one top-level scale for `final_norm_output` (not per-layer).
- Add a generic `ssm_quant_dequant(float v, float scale)` inline helper to
  `ssm_backbone.c` and call it right after `u[]`, `z[]`, and `block_out[]`
  are each fully computed, and after `normed[]` in `SSMBackbone_ProcessFrame`.
- Parity and footprint, same workflow as Phase 2, against `boundaries`'
  own quantized Python reference.

### Phase 4 -- item 5 (scan, weight+activation) -- the hard one

- Same scale-export mechanism as Phase 3, for the `scan` group's tensors.
- The loop surgery: insert `ssm_quant_dequant` calls on `delta[]`, `B[]`,
  `C[]` after their loops (easy, same as boundaries' arrays), and inline
  inside the innermost `for c / for n` loop for `A_bar`, `B_bar`, and the
  updated `h[c][n]` -- and on the scalar `y_c` at the point it's computed,
  before the `+ u[c]*D[c]` and gate multiply. This is the loop identified
  above as invasive; go slowly and re-verify parity after each tensor added,
  rather than adding all four quantize points and debugging a combined
  failure.
- Given `findings/522`/`523` already flagged `concat_mean_last` + kNN as a
  real secondary weak point for `scan`, and `max` pooling as fragile under
  a static scale: if the on-device parity check has any flexibility in
  which pooling to spot-check first, `mean` pooling is the one validated
  clean across every Python variant -- confirm that one before spending time
  chasing the already-known-fragile combinations on hardware.

### Phase 5 -- item 6 (all, weight+activation)

- Very likely a union of Phase 3's and Phase 4's changes with no new design
  work, once both exist independently and are verified. Confirm this
  assumption once Phase 4 is done rather than assuming it holds without
  checking.

### Phase 6 -- consolidate

- Build the results table `06_phase_5...`'s handoff manifest asks for:
  accuracy and footprint at each rung, per scheme, now with real device
  numbers alongside the Python predictions from `findings/520`-`523`.
- Revisit percentile-clipped static scales (`findings/523`'s deferred
  discussion) here, informed by which schemes' real-hardware numbers (if
  any) actually warrant the extra complexity -- this was deliberately left
  for exactly this point rather than decided in the abstract.

### Phase 7 -- true int8 backbone (post-deployment-matrix, real integer arithmetic)

Motivated and Python-validated in `findings/541` -- not a continuation of
items 1-6 above, which are all fake-quant (round, then compute in fp32).
This is genuinely different arithmetic and needs real new C, not a macro
swap:

- **LUT export.** Six 256-entry `const int8_t[256]` tables (softplus x2
  layers, silu-at-conv x2 layers, silu-at-z-gate x2 layers), matching
  `true_int8_sim.py`'s `build_lut`.
- **Calibration-constant export.** The hook-derived scales
  (`dt_proj_out`, `conv_out`, `x_proj_delta_low_out`, `norm_out` per layer)
  plus the discretize-step scales (`A_bar`, `B_bar`, `h` per layer) --
  roughly double the scale fields `boundaries` added, none of it reusable
  from that work since these are different tensors.
- **`h`'s storage type genuinely changes.** Every prior scheme kept
  `SSMBackbone_State.h[SSM_D_INNER][SSM_D_STATE]` as `float`; this needs it
  as `int8_t` or `int16_t` for real, in the struct definition in
  `ssm_backbone.h` and in `SSMBackbone_Reset`, not a macro-level swap.
- **Suggested width to build first:** int8, not int16, despite `findings/541`
  showing `euclidean` fails there -- `euclidean` isn't a deployment target
  (Phase 8), and int8 is the harder, more informative case for the
  "find the limits" goal this was built for. Build int16 second, as the
  fallback / comparison point, not the default.
- Apply the same one-change-at-a-time verification discipline as Phase 4's
  loop surgery -- this touches more of `ssm_block_step` than any prior
  phase, and the struct-position class of bug from Phase 3/4's work is a
  real risk here too, with more new fields than either of those had.

### Phase 8 -- anomaly-scoring head (euclidean, knn_clustered_16)

Nothing before this phase touches scoring -- every prior phase produces an
embedding, never a decision. From `src/eval/auc_pauc.py`, read directly
rather than assumed:

- `euclidean`: `centroid = train_emb.mean(axis=0)`;
  `score = ||query - centroid||`. One 64-float reference vector.
- `knn_clustered_16`: 16-cluster KMeans fit on `train_emb`;
  `score = min(||query - centroid_k||)` over the 16 centroids. 16x64 floats.

**Critical design point, not optional:** `train_emb` in the existing
pipeline is fp32-model embeddings. Whichever backbone scheme actually ships
(a Phase 1-6 fake-quant scheme, or Phase 7's true-int8 backbone) must be
used to RECOMPUTE `train_emb` -- and the thresholds in
`thresholds_same_machine.json` -- before exporting the centroid/cluster
centers. Comparing a quantized query embedding against an fp32-computed
reference set is exactly the domain-mismatch class of bug this project has
repeatedly caught and fixed elsewhere; it must not ship unnoticed here.

Threshold: `runs/case1/16662b29beb3/thresholds_same_machine.json` already
has computed thresholds (percentile, EVT/GPD, parametric, KDE, MAD, IQR --
`src/eval/thresholds.py`) for `mean` pooling x both heads. Pick one method
(EVT is the most principled for a low false-alarm target, per that file's
own docstring) once `train_emb` is recomputed under the shipped scheme.

C sketch: new `anomaly_head.c`/`.h`, called after `SSMBackbone_GetPooled()`
-- straightforward L2-distance loops (64 or 1024 multiply-accumulates),
nothing like the backbone's cost. Open decision: transmit the raw score
(more flexible, re-thresholdable later) or just the binary decision
(simpler protocol) -- this project has consistently valued being able to
re-analyze after the fact, which favors the raw score.
